01 · Bối cảnh

Hai nhánh đã thật sự rẽ — đo trước khi đụng vào

Câu hỏi đầu tiên không phải "merge thế nào" mà "có gì để merge không". merge-base trả về 14ffaec (30/07): một điểm nằm giữa, không phải đầu nhánh nào. Nghĩa là cả hai bên đều đã đi tiếp — upstream 106 commit, fork 13 commit — nên đây là merge thật, không phải fast-forward.

Đo được gì trước khi merge

  • git merge-base = 14ffaec — nằm giữa, nên không bên nào chứa bên nào.
  • rev-list --count orca ^main = 106 · chiều ngược lại = 13.
  • 13 commit của fork chạm đúng 10 file — đủ nhỏ để liệt kê hết bằng tay.
  • Trong 10 file đó, 5 file là đường cài: README, bootstrap.sh, bootstrap-fork.sh, install.sh, install-harness.sh.

Vì sao phải liệt kê trước

Danh sách file riêng của fork chính là bài kiểm tra sau merge. Không có nó thì "merge xong, có vẻ ổn" là toàn bộ bằng chứng.

  • Có danh sách → sau merge diff với upstream phải ra đúng tập đó.
  • Dư một file → merge kéo ngược thứ gì đó của upstream vào.
  • Thiếu một file → merge đánh rơi thứ gì đó của fork.

Chi tiết: llmwiki/wiki/draft/cave/080926-merge-upstream-setup.md

02 · Xung đột

Ba xung đột, ba câu hỏi khác nhau

Không cái nào giải được bằng --ours hay --theirs. Mỗi cái hỏi một chuyện riêng: hunk này có trộn hai thay đổi độc lập không · hai bản có quan hệ bao hàm không · index có còn khớp file trên đĩa không.

FileHai bên sửa gìQuyết địnhBằng chứng
install.sh Upstream thay đường dẫn cứng bằng biến $OVERSTACK_DIR; fork đổi REPO_RAW sang repo của chính nó. Lấy phần cấu trúc của upstream, giữ REPO_RAW + SKILLS_REF của fork. Hai thay đổi độc lập nằm chung một hunk — chọn cả file theo một bên là mất bên kia, im lặng.
egress-guard.py Cả hai cùng vá bug guard chấm host trong toàn bộ command string nên chặn nhầm commit message. Lấy trọn bản upstream. git show hai bản ra file rồi diff: upstream chứa đúng fix của fork, cộng _NOT_A_TLD + bare_ok. Sau khi giải, file khớp nguyên văn bản upstream.
llmwiki/wiki/index.md Fork thêm 2 dòng provenance; upstream tách/đổi tên thành các dòng có hậu tố -1319b8e1. Lấy khối upstream. Đọc file thật sau merge: 300726-session-provenance.md là phiên 0121bc61 — giữ dòng của fork sẽ thành index trỏ sai. index_sync xanh sau khi lấy upstream.

Chỗ suýt mất — install.sh

# <<<<<<< HEAD (fork)
REPO_RAW="${REPO_RAW:-https://…/dragonwar000/stackoverflow/main}"
mkdir -p "$ROOT/llmwiki/html"
# ======= (upstream)
REPO_RAW="${REPO_RAW:-https://…/Rheinmir/setup/orca}"
mkdir -p "$ROOT/$OVERSTACK_DIR/html"

# → giải: dòng trên của fork + dòng dưới của upstream

Lấy --theirs thì người mới curl về sẽ cài bản upstream chứ không phải bản fork. Lấy --ours thì mất cải tiến layout. Cả hai đều không báo lỗi.

Chỗ suýt mất — egress-guard.py

Hunk chỉ cho thấy chỗ hai bên chạm nhau, không cho thấy quan hệ bao hàm. Phải kéo cả hai bản ra rồi so:

git show origin/orca:harness/scripts/egress-guard.py > /tmp/a.py
git show stackoverflow/main:harness/scripts/egress-guard.py > /tmp/b.py
diff -u /tmp/b.py /tmp/a.py   # upstream ⊃ fork
  • Bản fork: thu phạm vi về đúng segment có lệnh net.
  • Bản upstream: có đúng phần đó + lọc bootstrap.sh, uat.env, spec.loader khỏi bị đọc thành hostname.

03 · Dọn thêm

Hai việc nằm ngoài conflict marker

Git chỉ dựng marker ở chỗ hai bên sửa cùng dòng. Thứ nguy hiểm hơn là chỗ hai bên có chính sách khác nhau mà git không thấy — ở đây là file build artifact, và các con trỏ về repo gốc.

54 file .pyc

Upstream còn track build artifact dưới skills/last30days/; fork đã gỡ 127 file .pyc và chặn __pycache__/ từ commit aebb940. Merge kéo chúng vào lại như file mới — không xung đột, không cảnh báo.

git ls-files | grep -c '\.pyc$'   # 54 sau merge
git rm -r --cached -q $(git ls-files | grep '\.pyc$')
git ls-files | grep -c '\.pyc$'   # 0

Con trỏ về repo gốc

Cây đã merge còn 7 chỗ hardcode Rheinmir/setup ngoài đường cài. Câu hỏi đúng không phải "có nên đổi không" mà "chúng mới xuất hiện hay đã có từ trước".

  • version.json, .template-manifest.json — nguồn template-sync, fork vốn đã trỏ upstream.
  • fdk-kit.sh, harness-events.py, fresh-install-smoke.sh, gen-converters.py, build-overstack-docs.py — git cat-file -e trên stackoverflow/main cũ: tồn tại y hệt.
  • Kết luận: merge không sinh drift định danh mới.

04 · CI tại local

Chạy trọn luồng CI trước khi push, không sau

Rule FDK: trước khi ship push thì đối chiếu luồng CI GitHub tại local. Ở đây nó không phải nghi thức — workflow harness.yml chỉ trigger push trên nhánh orca, nên push vào main của fork không chạy CI nào. Local là cổng duy nhất.

Kiểm cú pháp trước khi chạy gate

Merge 413 file thì lỗi rẻ nhất là file dính conflict marker hoặc gãy cú pháp. Quét trước, chạy gate sau:

# 0 file còn marker
grep -rln '^<<<<<<< HEAD' --exclude-dir=.git .

# mọi .py / .sh đổi đều parse được
for f in $(git diff --cached --name-only --diff-filter=ACM | grep '\.py$'); do
  python3 -c "import ast;ast.parse(open('$f',encoding='utf-8').read())"
done

Vì sao local là cổng duy nhất

  • harness.yml khai on.push.branches: [orca] — fork đẩy vào main thì workflow không chạy.
  • Trigger pull_request vẫn hoạt động ở mọi nhánh — nên đường PR có CI, đường push thẳng thì không.
  • Chọn push thẳng vào main = tự nhận trách nhiệm chạy hết cổng ở local. Đó là việc đã làm.

06 · Nợ mở

Cái chưa đóng, và vì sao để lại

Ghi ra thay vì lặng lẽ vá — mỗi món đều đổi hành vi của repo theo cách người chủ nên tự quyết.

1 · CI không gác nhánh main của fork

Sửa một dòng là xong, nhưng nó đổi hành vi CI của repo (thêm lượt chạy trên mọi push), nên để người chủ quyết:

# .github/workflows/harness.yml
on:
  pull_request:
  push:
    branches: [orca, main]

Trước khi đổi: đường PR đã có CI sẵn — nếu fork chuyển sang land qua PR thì món nợ này tự hết.

2 · Nhánh feature cũ của upstream

Repo gốc còn ~30 nhánh, trong đó vài nhánh mang commit chưa nằm trong orca:

  • Rheinmir/open-knowledge-format · Rheinmir/skill-spector — mỗi nhánh 14 commit, dừng từ tháng 6.
  • master (13) và main (5) — nhánh lịch sử, không phải nhánh phát triển.
  • Đợt này chỉ kéo orca — nhánh mặc định, nơi 106 commit mới thật sự nằm.
